# 第 3 项最终帧与初始化时间预算

最终保留功能若为第 3 项，UFM A/B 几何帧的保守上界沿用完整 3 往返测试的 **338665 clocks = 6.77330 ms**。这包含 UFM、LCD 读写和绘图状态机开销，尚未包含绘图接受之前可能排队的一次反显命令。

## 一次反显命令的开销

生产 `lcd_bus_phase` 默认写事务为 setup 4 + WR active 6 + hold 6，总计 **16 clocks**（从 bus 接受到 done）。设 renderer 在时钟 S 的 IDLE 分支选择反显命令，时序如下：

|时钟|事件|
|---|---|
|S|进入 INVERSE_SEND，锁存本次 A7/A6|
|S+1|bus 接受命令|
|S+11|/WR 上升，LCD 锁存命令|
|S+17|bus done|
|S+18|renderer 观察 done 并回到 IDLE|
|S+19|可接受已 pending 的绘图请求|

相对同一 IDLE 周期直接接受绘图，单命令纯排队开销为 **19 clocks**。报告统一预留 **20 clocks = 0.400 µs**，覆盖采样对齐。因此等待一次反显命令的最坏请求帧预算为 **338685 clocks = 6.77370 ms**，相对连续模式 60 ms 步进余量 **53.22630 ms**。

补测四个空闲相位边沿的“事件 → 命令完成”均为 **19 clocks**，与该握手推导一致。

## 绘图忙时的报警事件

输入先经 `alarm_now/inverse_requested` 寄存。反显命令只在绘图状态机回到 IDLE 后发送，优先于下一个 pending 请求。若事件恰好落在 IDLE/请求接受边界，新请求可能先开始，但此时上一帧只剩最多数个时钟；总阻塞仍可按一整帧加输入/状态边界时钟预算。

对“事件发生 → LCD 命令事务完成”采用几何帧加 **24 clocks** 的保守界限：**338689 clocks = 6.77378 ms**。该预算包括输入寄存、IDLE 决策、bus 启动和 done 观察；/WR 锁存命令早于事务完成，因此实际“发令”不会更晚。一个相位事件与一个解除事件落在绘图中的专项已验证：命令延后、两帧共 2112 字节与 Python 参考一致、命令不改变显存。

上述两个忙中案例分别实测 **21876 clocks** 和 **12802 clocks** 的事件至命令完成延迟。测试使用 1 MHz 时间基准验证真实 250 ms 相位，报告中比较与保守界限采用 RTL clock 数；这些案例不是遍历所有角度后的最坏值。

## 初始化

真实 50 MHz ÷ 50000 的初始化测试：复位至整屏显示完成 **2373268 clocks = 47.46536 ms**（含 5 个 reset 时钟）；其中第一次 UFM 请求至背景复制/display-on **173137 clocks = 3.46274 ms**。UFM 串行读取子耗时 **3.06442 ms**。反显不改变初始化的复制过程；若初始化完成时恰有反显请求等待，额外命令也可预留上述 **20 clocks / 0.400 µs**。

完整分类和初始化证据见 `step2_verification.md`、`runs/step2_production_copy2/basic/simulation.log`；反显时序实测见 `runs/step3_alarm_latency/simulation.log`。
