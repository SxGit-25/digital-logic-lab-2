# 第 5/6/7 项 UI 追加周期

独立测试文件 `tb_p5_ui_timing.v`，候选 `design/radar_lcd_micro_ui_specialized.v`。未修改原有 UI 测试及运行中的生产测试源。

启用 `P5_UFM=1`、生产 reader + base word mem、`P5_INVERT=1` 且 alarm=0；直接使用生产 `lcd_bus_phase`，默认写事务忙时长 16 clocks。计量起点为第一次 `UI_START`，终点为本请求 `done`，用物理 `$time` 差除以 20 ns 避免同沿监测顺序竞争。

|单独启用项|列数|写事务数|追加 clocks|50 MHz 耗时|
|---|---:|---:|---:|---:|
|100 动态数字|42|168|3026|60.52 µs|
|010 模式字|28|112|2017|40.34 µs|
|001 等级条|20|80|1441|28.82 µs|

每列发页、高列、低列、数据四次写事务。每事务含 16 clocks bus 忙时长和 2 clocks 状态机握手；每区域另一个 UI_START 时钟。因此单区域为 cols×4×18+1；数字含两个区域，为 42×4×18+2。

三项各测试 3 个请求，首次/最新 pending/末次快照正确、合并恰为 1；逐列数据复用独立 Python `ui/check_core_stream.py` 比较全部 PASS。计时的三个请求各项数值完全一致。日志与输入源码 hash 见 `runs/ui_real_timing2/`。

仅作为候选报告，若按几何上界 338665 clocks 和一次反显 20 clocks 相加，各项总帧预算分别为：数字 **6.83422 ms**，模式字 **6.81404 ms**，等级条 **6.80252 ms**。是否保留仍以资源及完整整机门槛判定。

本专项的 LCD 输入数据固定为零，用于真实 bus 握手计时和 UI 列流比较；它不用于替代底层雷达显存的完整 RAM 参考回归。
